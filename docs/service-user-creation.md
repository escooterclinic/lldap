# Atomic non-human account creation

The new `createServiceUser(user: CreateUserInput!, expectedBotGroupUuid: String!)`
mutation uses the existing directory administrator authority. It does not change
`createUser`, add an HTTP endpoint, issue credentials, enroll SSH keys, grant
application access or introduce another authorization store.

Within one existing-authority database transaction it positively resolves the
exact immutable expected group UUID and literal `Bot` marker, conditionally locks
and updates that group's modification time, then inserts the user, attributes
and exact membership. A missing, renamed or ambiguous marker and any write
failure roll back the entire creation. There is no committed unmarked user.
The caller's UUID is canonical and nonzero. Other roles are denied before any
backend call. Infrastructure errors are logged with an error ID; their raw
strings are not returned. Successful creation logs the current actor, new user ID
and immutable marker UUID. Existing-name collisions do not adopt or relabel users.

## Managed onboarding prerequisites

1. The governing owner declares each distinct service purpose and approved name.
   A caller-supplied name, an existing similarly named account or an existing bot
   never proves ownership. Directly inspect each existing identity; an unknown
   collision blocks creation rather than being adopted.
2. Positively verify the current trusted Bot group's immutable UUID from the
   governing directory and retain that explicit expected authority in the owner's
   declaration. Do not replace an expected UUID with the first name match after
   deletion/recreation.
3. Invoke this admin-only mutation and request `id`, `uuid` and the membership's
   `id`, `uuid`, `displayName`. Re-read the exact immutable new user and matching
   marker after the transaction. Record the returned immutable identity in the
   existing owning source/registration declaration; the proposed name alone is
   never an access grant.
4. Only after that committed marker/readback may an owning provisioner issue a
   distinct managed credential. Exact access-matrix permissions, canonical target
   scope, source address, fixed owner command/profile and managed target host key
   remain separate required checks. Registration-read, native-offboarding and
   IP-policy-delivery identities must not borrow one another's credentials.
5. Connect reconciliation to its existing owner lifecycle, preserving schedules
   and bounds. This API supplies atomic creation, not a claim that every owning
   service has already wired unattended onboarding. No new timer is installed.

## Tests and build

`bash scripts/test-atomic-service-user.sh` runs the complete native SQL-backend
and GraphQL crate suites. When cargo is absent on a disposable runner, it
bootstraps Rust1.91.0 using the vendor installer into that job's own directories,
without changing system toolchains or shell profiles. The existing SQL backend and SQLite unit fixtures are retained; no datastore
migration occurs. Fresh CT170 native config/process reads established its live
authority is PostgreSQL17.11, not SQLite. `scripts/test-service-postgres.sh`
requires a private run-owned PostgreSQL17 cluster and explicitly executes the
otherwise ignored backend-specific rollback/concurrent-reader test.

The same script's optional `--build-artifact /absolute/new/output` creates the
Linux release binary, schema generated by that binary, lockfile checksum and
toolchain/architecture receipt. It refuses non-Linux artifact mode. It never
changes a live directory. The generated schema remains the sole declaration.

## Root-orchestrated deployment boundary

Before replacement, establish the actual unit executable, configuration, assets,
binary hash, database schema and governing updater from the subject. Prove a
working independent access route which does not require this directory before
any service interruption. The existing scoped identity approval does not waive
that fallback or justify an unbounded restart through one's own access rail.

Mark the service intentionally off/mask it before stopping and taking any
rollback database snapshot; name its restarter. Keep the original binary,
metadata, unit/configuration/assets and a consistent existing-database backup.
For CT170 use a consistent native PostgreSQL custom archive; no live SQLite
copy is applicable. Preserve all
existing users, credentials, memberships, identities and schema version.

Stage the reviewed Linux artifact from its owning source, verify its checksum,
ELF platform,0.6.3compatibility and generated schema, then use only the reviewed
[package-diversion owner](../esc-overlay/ACTIVATION.md). Vendor unit/drop-ins and
actual argv are preserved; a changed vendor contract selects the CURRENT package
and atomic API PENDING. Restore service availability as
a hard exit condition and verify existing admin/LDAP controls plus the new
admin-only atomic-creation isolated subject/control. Confirm normal human
creation is unchanged. A failure rolls back the binary and restores the prior
service; any required data restore follows the same intentionally-off guard.
No credential is issued before the newly persisted non-human marker is proven.

Record final deployed source/artifact hashes in the private operational record.
A source build, unit pass or archive alone is not a live activation or a proof
of unattended updater convergence. Do not deploy until the actual updater
preserves this owner artifact reproducibly. All cadence, retention and grants
not specifically approved remain unchanged.
